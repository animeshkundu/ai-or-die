# macOS boot service for ai-or-die (launchd LaunchAgent) — 2026-11-27

Local-machine setup, not a repo feature. Records why this Mac runs ai-or-die
from a hand-written LaunchAgent instead of `ai-or-die service install`, and the
traps that shaped the plist. Nothing in `src/supervisor/` changed.

## Why not the supported service

`ServiceInstaller` generates a unit that runs
`node ~/.ai-or-die/bin/ai-or-die-supervisor.js`, and `bin/supervisor-service.js`
spawns `STABLE_SERVER_BIN` = `~/.ai-or-die/bin/ai-or-die-server` — a **prebuilt
SEA binary**, not the JS entry (`src/supervisor/constants.js:16`,
`src/supervisor/server-manager.js:47`).

No such binary exists for darwin-arm64:

- `.github/workflows/build-binaries.yml` matrix = `ubuntu-latest` (linux-x64)
  and `windows-latest` (win32-x64) only.
- Release `v0.1.112` assets: `ai-or-die-linux-x64`, `ai-or-die-windows-x64.exe`.
- `AutoUpdater.platformAssetPattern()` (`src/supervisor/autoupdater.js:38`)
  matches `ai-or-die-server-<plat>-<arch>` → `_pickAsset()` returns **null** on
  darwin, so the updater cannot even self-heal a missing binary.

Reproduced pre-fix:

```
$ AI_OR_DIE_HOME=/tmp/aod-svc-test node bin/supervisor-service.js --port 7891
Error: Cannot find module '/tmp/aod-svc-test/bin/ai-or-die-server'
[supervisor-service] failed to start: server exited before READY
```

`bin/supervisor.js` (the npm bin) does NOT have this problem — it spawns
`bin/ai-or-die.js` from the package. So the npx path works on macOS and the
service path does not. That asymmetry is the whole reason for this workaround.

## What runs instead

`~/Library/LaunchAgents/com.ai-or-die.plist`, hand-written (NOT regenerated by
any tool — editing it is safe, and `ai-or-die service install` would overwrite it):

```
node <nvm>/v26.12.0/bin/node <nvm>/v26.12.0/lib/node_modules/npm/bin/npx-cli.js \
  --yes ai-or-die@latest --port 7778 --mesh --disable-auth
```

- `RunAtLoad` + `KeepAlive` + `ThrottleInterval 30`.
- Logs: `~/.ai-or-die/logs/launchd-{out,err}.log` (created lazily; the dir is
  pre-created because launchd will not mkdir for `StandardOutPath`).
- Verified end-to-end with a throwaway copy of the same plist (label
  `.ldtest4`, port 7898, sandboxed session dir, still no shell): `launchctl
  list` showed a real PID with `LastExitStatus = 0`, the server bound its port,
  logs landed in `StandardOutPath`/`StandardErrorPath`, and the manual instance
  on 7777 answered `200` at the same time. Loaded, exercised (crash respawn +
  `kill -STOP` hang probe), then unloaded — the real label was never loaded, so
  the known-good manual instance was never disturbed.

Deliberate choices:

| Choice | Reason |
|---|---|
| Absolute `node` + absolute `npx-cli.js` | launchd does not source `.zshrc`; `env -i zsh -lc` proves nvm is absent without it (`.zshenv` only loads cargo, `.zprofile` only homebrew). |
| **`--port 7778`, fixed** | Deliberate separation from a manual `npx ai-or-die` on the default 7777 — two instances on one port is the worst case (see trap 2). Verified both up at once: manual 7777 → `200`, boot instance on its own port → `200`. |
| **`AI_OR_DIE_SESSION_DIR=~/.ai-or-die/boot-sessions`** | `sessions.json` is rewritten whole (atomic tmp+rename, last writer wins), so a shared store would have the two instances clobbering each other's session list on every save and restart. Created by `initializeStorage()`. |
| **`AIORDIE_MESH_HOSTNAME_SUFFIX=boot`** + **`AIORDIE_MESH_STATE_DIR=.../ts-state-boot`** | A tsnet node owns its state dir and hostname; the second node takes `aiordie-anilocal-boot` and its own identity dir (which also relocates the derived `peers/egress/quarantine` files). Both knobs were added to `MeshManager` for this setup and default off. The new dir is **unenrolled**, so the first boot logs `Mesh: NOT ENROLLED` and runs localhost-only until a reusable tagged `AIORDIE_TS_AUTHKEY` is supplied once. |
| Explicit `PATH` in the plist | Node, not npx, is the entry point, so npm's PATH augmentation never runs — but the child still shells out for `claude`/`copilot`/`git` discovery. |
| **No** `--prefer-offline` | That flag bypasses staleness checks for cached data (npm docs, `prefer-offline`), so `@latest` would resolve from a stale cached packument and a reboot would never pick up a release published while the machine was off. Offline at login instead makes npx fail, and KeepAlive + `ThrottleInterval 30` retries until the network is up. |
| `ai-or-die@latest` (no pin) | Reboot = upgrade. Auto-update is intentionally not implemented (user decision 2026-11-27); there is no PTY-preserving swap on this path. |
| `--disable-auth` | Kept, matching the previous manual command. Surface = tailnet + any local process on 127.0.0.1. |

## Tailnet identity is derived, not configured

`MeshManager` uses `` `aiordie-${os.hostname()}` `` sanitized
(`src/mesh-manager.js:64`). `hostname` = `ani.local` → `aiordie-anilocal`, which
is the node already enrolled in `~/.ai-or-die/ts-state` (`tailscaled.state`).
That is why **no `AIORDIE_TS_AUTHKEY`** appears in the plist: identity persists
in the state dir, so a boot does not need the key (and a plist is world-readable
— secrets must never live there). Verified: `peers.json` shows
`self.hostname = aiordie-anilocal`, `dnsName = aiordie-anilocal.nilgiri-grouper.ts.net`.

Note `src/mesh-manager.js:498` prints an enroll hint mentioning the variable;
that is the only `AIORDIE_MESH_*`-adjacent knob and there is no
`AIORDIE_MESH_HOSTNAME`. Hostname comes from `os.hostname()`.

## Traps verified while doing this

1. **`launchctl load` of a stale plist silently keeps the old job.** This Mac
   still had `~/.ai-or-die/service.json` from 2026-10-03 pointing at a dead bunx
   path (`/private/var/folders/.../bunx-501-ai-or-die@latest/...`) with
   `"stable": false` and no plist on disk. Always `launchctl unload` before
   `load`, then confirm with `launchctl list com.ai-or-die` (a real PID, not `-`).
2. **Port collision = silent flap, so the boot instance gets its own port.**
   Two instances sharing a port: `EADDRINUSE` exits `NON_RETRYABLE_EXIT_CODE`
   (78), `bin/supervisor.js` calls `process.exit(78)`, and launchd restarts the
   job every `ThrottleInterval` (30s) forever — logged nowhere obvious. Hence
   `--port 7778`.
3. **`~/.ai-or-die/ts-state` and `~/.ai-or-die/mesh/` are per-node state.** Two
   `--mesh` instances on one machine each need their own tsnet identity. Two
   env vars now cover that (added for this setup, both default-off so existing
   installs are unchanged — `src/mesh-manager.js`):
   `AIORDIE_MESH_HOSTNAME_SUFFIX=boot` → `aiordie-anilocal-boot`, and
   `AIORDIE_MESH_STATE_DIR=~/.ai-or-die/ts-state-boot`. Relocating the state dir
   also moves the derived `peers.json` / `egress.json` / `quarantine.json`
   (they describe one sidecar and `stop()` deletes them, so a shared
   `<base>/mesh` had the two nodes erasing each other's view — confirmed by
   `egress.json` being rewritten with the new sidecar's pid on start).

   **The enroll key is the one thing that is NOT automatic:** a fresh state dir
   is unenrolled, so the boot node starts localhost-only (`Mesh: NOT ENROLLED`,
   the port still serves) until `AIORDIE_TS_AUTHKEY` is supplied once. Do not
   copy `tailscaled.state` between dirs — one identity must not be presented by
   two nodes.
4. **LaunchAgent ≠ boot.** It is a *login* job. Boot-start requires either
   auto-login (`sysadminctl -autologin set`, allowed here because FileVault is
   off) or a LaunchDaemon (root, unsupported by this repo, and wrong anyway —
   `sessions.json` and CLI credentials are per-user).
5. **nvm-pinned node.** Reinstall/edit the plist after a Node upgrade; the path
   is absolute by design.
6. **Crashes recover; hangs do not.** Verified by killing the server child:
   `bin/supervisor.js` respawned it in 3s on the same port
   (`[supervisor] Server exited unexpectedly (signal SIGKILL)`), escalating to
   tier-1 60s / tier-2 5min on crash loops. Verified the other way with
   `kill -STOP`: the frozen child kept the port and answered nothing (`curl`
   timed out) and for 20s neither the supervisor nor launchd acted — launchd
   only watches for *exit*. A hang watchdog would need to live outside
   `bin/supervisor.js` (the server owns `/health`; the supervisor link is the
   IPC channel only). Codes 0 and 78 are not respawned by the supervisor; they
   escalate to launchd's restart-on-exit.

## If the supported path becomes viable

Adding `darwin-arm64`/`darwin-x64` to `build-binaries.yml` and publishing
`ai-or-die-server-darwin-*` assets would let `npx ai-or-die service install
--port 7777 --mesh --disable-auth` replace this plist, giving staged-tree
stability + supervisor autoupdate + PTY-surviving swaps. That needs a spec/ADR
change; it was explicitly deferred on 2026-11-27.

What's broken on main

Branch main @ 0780965 (v0.1.101). Findings below are measured, not inferred — sources cited per item.

Headline

criticalThe server leaks memory without bound, and the suite built to catch that has never once passed.

Every scheduled longevity run on main fails: 7 of 7 Nightly (4h) runs plus the Weekly 12h soak. All three platforms die identically:

FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory
Aborted (core dumped)  node test/longevity/harness/cli.js --duration=4h ...
exit code 134 (SIGABRT)  — ubuntu-latest, windows-latest, macos-latest

The soak OOMs about 68 minutes into a 4-hour window, so it has never reached its verdict and has never gated anything. Release on main is green throughout, which is why this stayed invisible.

Root cause 1 — eviction is age-only, with no count or byte ceiling

criticalsrc/server.js:6632 
const sevenDaysAgo = Date.now() - 7 * 24 * 60 * 60 * 1000;
...
if (currentLA >= sevenDaysAgo) {
  this._maybeRebuildEvictionHeap();
  return evictedCount;   // early-exit: nothing under 7 days is ever evicted
}

Age over seven days is the only eviction predicate. There is no cap on session count and none on retained bytes. Every accumulated session is minutes old, so the sweep early-exits on its first peek and frees nothing — forever.

Failure scenario: any client that creates sessions without deleting them drives the server to OOM. Nothing in the product bounds it; the MinHeap and pop-budget machinery around it is sound but is gated behind a predicate that never fires. This is a resource-exhaustion path, not merely a slow leak.

The same unbounded set is serialized to sessions.json every 30s, which is the disk curve above. One root cause, two symptoms.

Root cause 2 — the output buffer caps items, not bytes

latent / low real-world impactsrc/utils/circular-buffer.js + src/server.js:1482, 4060, 4708 
outputBuffer: new CircularBuffer(1000)   // 1000 items

// circular-buffer.js — byteLength is COMPUTED on every push...
this.byteLength += bytes;
// ...but never ENFORCED. Only `capacity` (item count) bounds the buffer.

The gap is real: nothing bounds the buffer in bytes. But I initially sized it wrong and am correcting that here.

Correction. The 262 MB figure (65,536,000 bytes per session) is synthetic. output-buffer-flood-workload.js:12 sets chunkBytes = 64 * 1024 and pushes directly into session.outputBuffer, bypassing the PTY path entirely. That number measures the workload's chosen chunk size, not product behaviour.

The same diagnostics payload carries the honest number. Sessions fed through the real path show 213 items / 51,333 bytes = 241 bytes per chunk. A genuine session therefore retains roughly 241 KB, not 64 MB — about 270x smaller than I first reported.

Revised assessment: a latent robustness gap worth closing cheaply (the class already computes the number it needs), but not a contributor to production memory growth. Downgraded from critical.

Calibration — what the synthetic numbers do and do not prove

read this before acting

Both headline magnitudes come from workloads that are adversarial by construction, and I want the limits of the evidence stated plainly rather than buried.

  • The ~59 sessions/sec is synthetic. The harness workloads create sessions and never delete them. No interactive user reaches 17,896 sessions in five minutes.
  • The 64 MB/session buffer is synthetic, as corrected above. Real chunks are ~241 bytes.
  • The CI OOM is fully explained by session count alone: ~59/sec × 4,080s ≈ 240,000 sessions × ~17 KB each ≈ 4 GB. That arithmetic matches the observed heap_used curve without needing any other leak.

Consequence I have to be straight about: I can no longer claim these explain the ~4 GB RSS you saw in real use. Under normal usage — a handful of sessions a day against a 7-day eviction window — neither mechanism produces meaningful growth. The earlier version of this report implied that link; it was not supported and I have removed it. Confirming the production cause needs /diagnostics (sessions.total + retention.output_buffers) pulled from your actual long-running server. That remains an open, separate question.

Independent critique — where my diagnosis was too strong

accepted corrections

A cross-lab critic reviewed the diagnosis. It landed several hits I accept rather than argue with:

  • My arithmetic is a consistency check, not causal isolation. Session objects account for ~300 MB of the 565 MB local heap. The remaining ~265 MB is unexplained, and I have not shown it is fixed rather than growing. “Sessions are sufficient to explain the OOM” is plausible; “no other mechanism is involved” is not established.
  • The ~17 KB/session figure was derived by subtraction, not by a post-full-GC retained-size measurement. It is an estimate, and I presented it with more confidence than the method supports.
  • A major confound I missed: sessions.json is re-serialized and rewritten every 30 s at ever-growing size (0 → 227 MB). JSON.stringify plus the write can transiently retain full copies, and overlapping async writes could queue several. Given the disk curve and the event-loop degradation, this could be contributing materially and is currently unmeasured.
  • “Unbounded” was imprecise. The 7-day rule does eventually bound retention — at 59 sessions/sec that ceiling is ~35.7 million sessions. It is operationally useless, but the correct framing is an admission/capacity problem, not an unreachable-object leak.
  • My option A was dangerous as stated. LRU eviction of durable sessions is not harmless cache eviction: a quiet, disconnected session may be deliberately awaiting reconnect from another device. Silent deletion would read as data corruption.

Better options it raised that I had not considered: admission control (reject new sessions with an explicit status at capacity, rather than silently destroying old ones); protected session classes (never auto-evict running or attached sessions); output degradation before session deletion (truncate or spool buffers first); and splitting the soak into a churn test (creates and deletes, detects true post-lifecycle leaks) plus a separate saturation test (asserts documented behaviour at capacity instead of waiting for OOM). Option B alone would turn the job green while leaving the production gap untouched.

Other verified defects

highWatcher wedges permanently on a failed start — src/utils/file-watcher.js:306 
if (this._watcher) return;                 // guard
this._watcher = chokidar.watch(...);       // assigned BEFORE the await
// ...4 listeners registered...
await new Promise((res, rej) => { ... onError = (e) => { cleanup(); rej(e); } });

If chokidar emits error before ready, start() throws but this._watcher stays non-null and is never .close()d. The native OS handle and four listeners leak. Worse: every later start() retry hits the guard and returns as if it succeeded, leaving a permanently dead watcher with no error surfaced.

Scenario: a transient permission error or an invalid root on Windows at startup — file watching is silently dead for the process lifetime, and the caller believes it is running. Verified by reading the code path directly.

mediumStream reader lock never released — src/utils/gguf-model-manager.js:139 
const reader = body.getReader();
try { ...fileStream.write... }
finally { await new Promise((r) => fileStream.end(r)); }   // no reader.cancel() / releaseLock()

A disk-write error or a throwing onProgress leaves the HTTP body stream locked and the socket open until it times out. Error-path only, on a one-shot model download, so impact is bounded.

lowPer-session map never cleaned — src/server.js:4527

_controlSessionSeq has .set() but no .delete() anywhere, while its sibling activityBroadcastTimestamps is cleaned in seven places including the DELETE handler and the eviction sweep. That asymmetry is the bug: session deletion appears to free memory but leaves this entry behind.

Honest sizing: it read 0 throughout my repro — these workloads never exercise the control-state path — so real-world magnitude is unproven and each entry is only a string key plus a number. A two-line fix, not a priority.

cleanCrash-capable error paths: no defects found

WebSocket handling caps frame size before JSON.parse, wraps parsing in try/catch, validates field shapes before property access, and attaches .catch() to async handlers. The PTY lifecycle tracks listeners in _ptyDisposables, disposes them on exit/stop, rolls back session.active when spawn rejects, and has a 30 s spawn watchdog. Windows process-tree reaping uses Job Objects.

One correction to my earlier mental model: uncaughtException dumps state and calls process.exit(1), so an uncaught throw is fatal. unhandledRejection only logs and continues.

Recommendation

Nothing is fixed yet, deliberately. My suggested order, for your call:

  1. file-watcher wedge — unambiguous, self-contained, no design question. Close this._watcher and null it on the error path. Safe to do now.
  2. Measure the confound before designing the session fix — run the soak with persistence disabled, and take post-GC retained-size heap snapshots at several session counts. That distinguishes session objects from sessions.json serialization pressure. Designing a capacity policy before knowing which dominates risks fixing the wrong thing.
  3. Then decide the capacity policy — admission control with protected session classes looks stronger than LRU eviction, because it does not silently destroy durable state a second device may be waiting to reattach to. Needs your input on the product contract.
  4. Split the soak into churn and saturation contracts so it can actually gate.
  5. gguf reader lock and _controlSessionSeq — cheap cleanups, fold into whatever branch comes next.

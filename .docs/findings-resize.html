Terminal geometry: findings and revised plan

Measured on Windows 11 via scripts/probe-multi-viewer-resize.js and scripts/probe-file-browser-geometry.js. The plan below is revision 2 — revision 1 was refuted by an independent critic and the refutation held up when I traced it.

root causeNothing owns “what should this session's geometry be”, and nothing re-asks when the inputs change.

Geometry is computed in one place — a single browser measuring its own container — and pushed at the PTY. Docked chrome that steals space, other viewers on the same PTY, and viewers arriving/leaving are all absent from that computation. Symptom 1 works only because it is the one case where a single browser's container is the whole truth.

Revision 1 was wrong. What the critique found.

retractedThe “dedup reclaims automatically” trick is a feedback loop, not a fix.

I proposed that a letterboxed viewer set target.last = applied, so its next measurement would differ and it would reclaim the PTY. Traced concretely, two attached viewers ping-pong forever:

desktop: last=38  capacity=163  -> next fit stimulus: 163 != 38  -> sends 163
phone:   last=163 capacity=38   -> next fit stimulus:  38 != 163 -> sends 38
                                 -> repeat, indefinitely

A phone emits visualViewport events constantly (scroll, URL bar, keyboard), so this thrashes in practice. Each flip resizes the PTY, which forces a full TUI redraw and can discard scrollback. The clever part was the defect.

Three further errors, all upheld:

  • Letterboxing only works when applied < capacity. When the desktop wins at 163 columns, a 390px phone cannot letterbox 163 columns — it must scale, pan, or scroll. I did not address that direction at all.
  • If letterboxing shrinks the observed container, the desktop subsequently measures 38 and can never reclaim. Outer capacity and inner rendered grid must be separate elements.
  • One variable cannot carry four states. localCapacity, lastAdvertised, authoritativeApplied and rendered are distinct; overloading target.last was the underlying mistake.

Also: Map<wsId,{cols,rows}> records no recency, so “most-recent-writer wins” was undefined as specified; and the Layer 1 pixel arithmetic was simply wrong — floor(a/c) - floor(b/c) ≠ floor((a-b)/c), and panel width is not the visible overlap during a transform transition.

Revision 2

Layer 1 — real layout, not pixel arithmetic (fixes symptom 4)

Drop the reserve-subtraction idea. Make the terminal's usable area an actual CSS layout region whose width changes when the panel docks, and let FitCoordinator observe that element.

This removes the whole class of error at once: no fractional column conversion, no sampling a transform mid-transition, no viewport > 1024 guess that can disagree with the panel's real responsive mode, and drag-resizing the panel is handled by ResizeObserver for free. reserve goes back to meaning only fixed chrome.

Independent of everything else. No protocol change. Safe to land first.

Also delete _refitAllTerminals() (file-browser.js:858) — fully implemented, never called. And _adjustTerminal()'s comment (“non-terminal surfaces overlay the terminal and never change its geometry”) is true on mobile and false above 1024px, which is plausibly how this survived review.

Layer 2 — explicit ownership, not incidental writes (fixes symptom 2)

The decisive correction: advertising capacity must not claim the PTY. Every incidental layout event — orientation, keyboard, panel drag, a retry, a reconnect — became an ownership claim under revision 1. That is the feedback mechanism, and explicit ownership removes it rather than damping it.

  • Each attachment advertises its capacity. This updates fallback state only.
  • Exactly one attachment holds an owner lease. Only the owner's capacity drives pty.resize.
  • Ownership transfers on a deliberate act — real user input from that device, or an explicit “take control” — not on a layout event. Typing on your phone is intentional; your phone's URL bar collapsing is not.
  • On owner disconnect, transfer deterministically to a surviving attachment and apply its capacity.
  • Server assigns a monotonic revision, serializes resize application per session, and validates geometry (integer, finite, positive, bounded). applied updates only after pty.resize succeeds. Clients ignore stale revisions.
  • A session epoch covers restart: the PTY survives but the attachment map does not, so persist applied geometry + revision alongside the session and have reconnecting clients re-advertise without claiming.

Keying must be (sessionId, connectionId, viewId), not wsId — one socket hosts multiple split panes, and splits.js:129 has its own send path that must use the same protocol or it becomes a direct feedback loop.

Layer 3 — non-owner rendering

  • Separate client state: localCapacity, lastAdvertised, authoritativeApplied + revision, rendered.
  • Applying authoritative geometry runs under a suppression guard that cannot itself emit a resize.
  • Render the grid in an inner element so the observed outer capacity element is never perturbed by letterboxing.
  • Capacity ≥ applied: letterbox. Capacity < applied: scale down or pan — letterboxing is impossible in that direction. For “glance at the phone”, scaling reads better than panning.
  • Below the 20x5 floor, send an explicit withdrawal. Otherwise a stale sub-floor desire sits in the server map and can become authoritative when the owner leaves.

Honest sequencing

Revision 1 implied this was a modest change. It is not. Splitting by cost and risk:

  1. Layer 1 — small, safe, high value. Fixes the file-browser occlusion you spotted. No protocol change, lands on its own.
  2. Owner-disconnect recovery — small, high value. Symptom 3 (the permanent wedge) does not need the full protocol: recompute on connection-set change and push to survivors. This is the worst user-facing bug and the cheapest real fix.
  3. Full multi-viewer ownership protocol — a real project. Epoch, revision, serialization, lease transfer, non-owner scaling, split-pane routing, withdrawal state, server validation and rate limiting. This is symptom 2, and it deserves an ADR superseding the single-viewer assumption in ADR-0046 rather than being bolted on.

I would land 1 and 2 now and write the ADR for 3 before writing any of its code.

Still unmeasured

Stated rather than glossed: phone orientation change, iOS soft keyboard (needs WebKit, not Chromium — bespoke visualViewport handling plus a Safari polling fallback), split panes, and reconnect-after-drop. The plan is designed to cover them; designed-to is not measured.
